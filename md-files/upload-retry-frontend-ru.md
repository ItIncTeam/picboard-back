[# Изменения в API загрузки файлов

Документ для фронтенд-команды. Описывает мутацию `retryUpload`, новые поля
в `completeUpload` и новый формат объекта ошибки.

**Начните с раздела [«Общий сценарий»](#общий-сценарий)** — там весь процесс
целиком, от выбора файла до готового поста. Остальные разделы раскрывают
отдельные шаги.

> ⚠️ **Есть ломающее изменение — см. [раздел 6](#6-ломающее-изменение-поля-ошибки-переехали-в-extensions).**
> Поля ошибки переехали в `extensions`. Без правки на клиенте перестанет
> работать обработка ошибок.

---

## Кратко

Раньше один неудачно загруженный файл ломал создание поста целиком: пользователь
терял четыре успешно загруженные картинки из-за одной сломанной. Теперь сломанный
файл можно перезагрузить отдельно, не трогая остальные.

Новая функциональность (разделы 1–5) **аддитивная**: существующие запросы
продолжают работать, новые поля появятся в ответе только если вы их запросите.

Одно изменение **ломающее** (раздел 6): формат объекта ошибки приведён
к стандарту GraphQL — `code` и `statusCode` переехали в `extensions`.

## Общий сценарий

Этот раздел — карта происходящего целиком. Детали по каждому шагу — в разделах
ниже.

### Состояния файла на сервере

```
                    initiateUploadBatch
                            │
                            ▼
                      ┌──────────┐
                      │ PENDING  │  uploadAttempts = 1
                      └──────────┘
                            │
                      PUT в S3 + completeUpload
                            │
                ┌───────────┴───────────┐
                ▼                       ▼
          ┌──────────┐           ┌──────────┐
          │  READY   │           │  FAILED  │
          └──────────┘           └──────────┘
                │                       │
         можно в createPost     retryUpload (если retryable)
                                        │
                                        ▼
                                  ┌──────────┐
                                  │ PENDING  │  uploadAttempts + 1
                                  └──────────┘
                                        │
                                  новый uploadUrl,
                                  тот же fileId и тот же ключ в S3
```

Ключевое: **`retryUpload` не создаёт новый файл.** Он возвращает существующую
запись в `PENDING` и выдаёт новую подпись для того же самого места в хранилище.
Поэтому `fileId` не меняется никогда.

### Шаг 1. Начало загрузки

```graphql
mutation {
  initiateUploadBatch(input: [
    { clientUploadId: "...", originalName: "photo.png",
      purpose: POST_IMAGE, mimeType: PNG, size: 245678 }
  ]) { clientUploadId fileId uploadUrl expiresAt }
}
```

Сервер создаёт записи в статусе `PENDING` и возвращает по одному presigned URL
на файл.

**Что сохранить у себя** — по каждому файлу:

```js
{
  blob,                    // сам File из input[type=file]
  fileId,                  // идентификатор на сервере
  uploadUrl,               // куда делать PUT
  expiresAt,               // до какого момента URL жив
  mimeType,                // то, что заявили — понадобится в заголовке PUT
  status: 'uploading',
  attempt: 1,
}
```

`clientUploadId` нужен только чтобы сопоставить ответы с вашими blob'ами —
сервер возвращает его как есть. Дальше он не используется: везде работает `fileId`.

> ⚠️ `size` считайте по **тому же самому blob**, который реально уйдёт в PUT.
> Если вы сжимаете или ресайзите картинку — считайте размер **после** обработки.
> Иначе `completeUpload` вернёт `Size mismatch`, и это не чинится повтором.

### Шаг 2. Загрузка в S3

```js
const res = await fetch(uploadUrl, {
  method: 'PUT',
  body: blob,
  headers: { 'Content-Type': mimeType },   // ровно то, что заявили в initiate
});
```

| Ответ S3 | Значение | Действие |
|---|---|---|
| `200` | байты в хранилище | → Шаг 3 |
| `403` | URL мёртв: истёк или не совпал `Content-Type` | → Шаг 4, **тот же URL повторять бесполезно** |
| `5xx`, `429` | временный сбой S3 | повторить PUT **на тот же URL** с задержкой |
| сетевая ошибка | связь оборвалась | повторить PUT **на тот же URL** с задержкой |

Подробнее про заголовки и подписи — [раздел 3](#3-правила-загрузки-в-s3).

### Шаг 3. Подтверждение

**Только после `200`.** Если вызвать раньше, сервер честно не найдёт объект
в S3 и пометит файл как `FAILED`.

```graphql
mutation {
  completeUpload(input: [{ fileId: "..." }]) {
    fileId status failedReason retryable
  }
}
```

| Ответ | Что делать |
|---|---|
| `status: READY` | готово, файл можно использовать в `createPost` |
| `status: FAILED`, `retryable: true` | → Шаг 4 |
| `status: FAILED`, `retryable: false` | повтор не поможет → предложить выбрать другой файл |

### Шаг 4. Повтор

```graphql
mutation {
  retryUpload(input: [{ fileId: "..." }]) {
    fileId uploadUrl expiresAt attempt
  }
}
```

Сервер возвращает файл в `PENDING`, увеличивает счётчик попыток и выдаёт новую
подпись **для того же ключа в хранилище**.

Обновите у себя `uploadUrl`, `expiresAt` и `attempt` — и **вернитесь на Шаг 2
с тем же blob'ом.** Ничего пересоздавать не нужно.

Всего на файл даётся **5 попыток** (первая + 4 повтора).

### Два уровня повторов — в чём разница

Это самое важное для понимания всего сценария.

**Уровень 1 — повтор PUT на тот же URL.** Бесплатно, мгновенно, без запросов
к бэкенду. Работает, пока `expiresAt` в будущем. Лечит нестабильную сеть
и временные сбои S3. Пробуйте это первым, 2–3 раза с нарастающей задержкой.

**Уровень 2 — `retryUpload`.** Нужен только когда URL стал непригоден: истёк
срок или S3 вернул `403`. Тратит одну попытку из пяти.

Ошибка, которой стоит избегать: дёргать `retryUpload` на каждый сбой сети.
Пять попыток кончатся за несколько секунд плохой связи, хотя ни одна из них
не была нужна.

Готовый код обоих уровней — [раздел 4](#4-рекомендуемая-схема-повторов-два-уровня).

### Когда `retryUpload` не поможет

| Ситуация | Почему | Что предложить пользователю |
|---|---|---|
| `retryable: false` (`MIME mismatch`) | заявили один тип, отправили другой — те же байты провалятся так же | выбрать файл заново |
| `retryable: false` (`Size mismatch`) | заявили один размер, отправили другой — в базе останется то же число | выбрать файл заново |
| Исчерпаны 5 попыток | лимит на файл | выбрать файл заново |
| `Upload verification failed` | сбой на стороне сервера; **файл в S3 скорее всего уже лежит** | сначала просто повторить `completeUpload` — часто этого достаточно |

Последняя строка — оптимизация: при серверном сбое перезаливать файл обычно
не нужно, достаточно ещё раз подтвердить.

### Что показывать пользователю

```
Загрузка… ──► ✅ Готово                       → status: READY
          └─► ⚠️ Ошибка  [Повторить (2 из 5)]  → FAILED, retryable: true
          └─► ❌ Ошибка  [Выбрать другой файл]  → FAILED, retryable: false
```

Подробнее про экран — [раздел 5](#5-логика-экрана-загрузки).

## 1. Новая мутация: `retryUpload`

Запрашивает новый presigned URL для файла, загрузка которого не завершилась.

```graphql
mutation RetryUpload($input: [RetryUploadInput!]!) {
  retryUpload(input: $input) {
    fileId
    uploadUrl
    expiresAt
    attempt
  }
}
```

```js
variables: {
  input: [{ fileId: "0d7f1a2b-..." }]   // до 10 файлов за вызов
}
```

### Что важно понимать

**`fileId` тот же самый**, что вернул `initiateUploadBatch`. Файл сохраняет свою
запись в БД и свой ключ в S3 — создаётся только новая подпись. Поэтому:

- ваша карта `fileId → File (blob)` остаётся валидной, перестраивать её не нужно;
- в `createPost` уходят ровно те же `fileId`, что и раньше;
- порядок вложений в посте не меняется;
- в S3 не остаётся мусорных объектов (перезапись по тому же ключу атомарна).

**`attempt`** — номер текущей попытки. Всего на файл даётся **5 попыток**
(1 первоначальная + 4 повторных). Когда лимит исчерпан, файл починить нельзя —
нужен новый `initiateUploadBatch`.

Это поле удобно показывать в интерфейсе: «Повторить (попытка 3 из 5)».

### Ошибки

Код ошибки читается из `errors[0].extensions.code` (см. [раздел 6](#6-ломающее-изменение-поля-ошибки-переехали-в-extensions)):

| Ситуация | `extensions.code` | HTTP |
|---|---|---|
| Файл не найден, не принадлежит пользователю, уже `READY` или удалён | `NOT_FOUND` | 404 |
| Лимит попыток исчерпан | `BAD_USER_INPUT` | 400 |
| Больше 10 файлов в запросе или пустой массив | `BAD_USER_INPUT` | 400 |
| Пользователь не авторизован | `UNAUTHENTICATED` | 401 |

> **Важно:** валидация работает на весь батч сразу. Если хотя бы один файл
> в запросе уже `READY`, чужой или исчерпал попытки — упадёт **весь вызов**,
> и вы не получите ни одного URL.
>
> Поэтому проще и надёжнее вызывать `retryUpload` по одному файлу за раз,
> если вы не уверены в статусах всех файлов батча.

## 2. `completeUpload` — два новых поля

```graphql
mutation CompleteUpload($input: [CompleteUploadInput!]!) {
  completeUpload(input: $input) {
    fileId
    status
    failedReason   # НОВОЕ — причина ошибки, null при успехе
    retryable      # НОВОЕ — поможет ли retryUpload
  }
}
```

### `retryable` — главное поле для UI

| Значение | Что показывать |
|---|---|
| `retryable: true` | кнопку **«Повторить»** → вызвать `retryUpload`, затем снова PUT |
| `retryable: false` | **«Выберите другой файл»** |

`retryable: false` означает, что **отправленные байты не соответствуют тому, что
было заявлено при `initiateUploadBatch`** — не совпал тип файла или его размер.
Повторная отправка того же файла провалится точно так же, сколько бы раз её ни
повторяли: в базе останутся те же самые заявленные значения. Такой файл нужно
добавлять заново через `initiateUploadBatch` с правильными метаданными.

### `failedReason`

Текстовое описание причины. Подходит для показа в интерфейсе или для логов:

| Причина | `retryable` | Что произошло |
|---|---|---|
| `Object not found in storage` | `true` | файла в S3 нет — PUT не дошёл |
| `Size mismatch: declared ..., actual ...` | **`false`** | заявили один размер, отправили другой |
| `MIME mismatch: declared ..., actual ...` | **`false`** | заявили один тип, отправили другой |
| `Upload verification failed` | `true` | временная проблема на стороне сервера/S3 |

Не завязывайте логику на текст `failedReason` — он может меняться.
Для ветвления используйте `retryable`.

> **Про `Size mismatch`.** S3 либо сохраняет объект целиком, либо возвращает
> ошибку — «недокачанных» объектов не бывает. Поэтому если вы дождались `200`
> перед вызовом `completeUpload`, несовпадение размера означает только одно:
> в `initiateUploadBatch` было указано одно число, а отправлены другие байты.
> Проверьте, что `size` считается по тому же blob, который реально уходит в PUT
> (частая причина — сжатие или ресайз картинки уже после подсчёта размера).

> **Про `Upload verification failed`.** Здесь файл в S3, скорее всего, уже лежит
> нормально — не долетел ответ от хранилища на стороне сервера. Прежде чем
> заново загружать файл, **просто повторите вызов `completeUpload`**: чаще всего
> со второго раза он вернёт `READY`, и перезаливка не понадобится.

## 3. Правила загрузки в S3

Эти правила действовали и раньше, но теперь от них напрямую зависит, увидит ли
пользователь ошибку.

### Заголовок `Content-Type` обязан совпадать

При PUT в S3 заголовок `Content-Type` должен **точно** совпадать с `mimeType`,
который вы указали в `initiateUploadBatch`:

```js
fetch(uploadUrl, {
  method: 'PUT',
  body: blob,
  headers: { 'Content-Type': mimeType },  // ровно то, что объявили в initiate
});
```

При несовпадении S3 вернёт `403 SignatureDoesNotMatch`. Ошибка выглядит как
проблема с авторизацией, но на самом деле это несовпадение заголовка.

### `completeUpload` вызывать только после успешного PUT

Дождитесь ответа `200` от S3 и только потом вызывайте `completeUpload`.

Если вызвать её раньше, сервер проверит наличие объекта в S3, честно его не найдёт
и пометит файл как `FAILED` — хотя через секунду файл бы долетел.

> Если вы сейчас наблюдаете «случайные» ошибки загрузки — начните проверку
> именно с этого места.

### Как трактовать ответы S3 на PUT

| Ответ | Что делать |
|---|---|
| `200` | успех → вызвать `completeUpload` |
| `403` | URL мёртв (истёк или несовпадение `Content-Type`) → **не повторять тот же URL**, запросить новый через `retryUpload` |
| `5xx`, `429` | временная проблема → повторить PUT **на тот же URL** с backoff |
| network error | то же самое — повторить на тот же URL |

## 4. Рекомендуемая схема повторов (два уровня)

Пока `expiresAt` ещё не наступил, повтор загрузки **не требует обращения к серверу
вообще**. Это экономит и запросы, и время.

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// Уровень 1: повторяем PUT на ТОТ ЖЕ URL. Бесплатно, без запросов к бэкенду.
// Решает проблему нестабильной сети.
async function putWithRetry(url, blob, mimeType, maxAttempts = 3) {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      const res = await fetch(url, {
        method: 'PUT',
        body: blob,
        headers: { 'Content-Type': mimeType },
      });

      if (res.ok) return 'ok';

      // 403 — URL истёк или не совпал Content-Type.
      // Повторять этот URL бессмысленно.
      if (res.status === 403) return 'needs-new-url';

      // 5xx / 429 — временная ошибка, пробуем тот же URL ещё раз
    } catch {
      // сетевая ошибка — тоже пробуем ещё раз
    }

    // экспоненциальная задержка + jitter.
    // jitter нужен, чтобы 10 параллельных загрузок не начали
    // повторяться одновременно и снова не столкнулись
    await sleep(2 ** attempt * 300 + Math.random() * 200);
  }
  return 'failed';
}

// Уровень 2: идём на сервер за новой подписью.
async function uploadOne(item, blob, mimeType) {
  let url = item.uploadUrl;

  for (let round = 0; round < 2; round++) {
    const expired = Date.now() >= new Date(item.expiresAt).getTime();

    if (!expired) {
      const result = await putWithRetry(url, blob, mimeType);
      if (result === 'ok') return true;
      if (result === 'failed') return false;
    }

    const [fresh] = await gql.retryUpload([{ fileId: item.fileId }]);
    url = fresh.uploadUrl;
    item = { ...item, expiresAt: fresh.expiresAt };
  }

  return false;
}
```

Ответы `initiateUploadBatch` и `retryUpload` совместимы по полям `fileId`,
`uploadUrl`, `expiresAt` — именно поэтому одна и та же функция загрузки работает
с обоими.

## 5. Логика экрана загрузки

Рекомендуемое поведение (так же работают Instagram и Twitter):

1. Показывать статус по каждому файлу отдельно.
2. Кнопку **«Создать пост»** держать неактивной, пока все файлы не станут `READY`.
3. У упавшего файла показывать кнопку по значению `retryable`:
   - `true` → «Повторить»
   - `false` → «Выберите другой файл»

`createPost` по-прежнему строго требует, чтобы **все** файлы были `READY`.
Это сделано намеренно: пост с отсутствующей картинкой сломан навсегда,
и пользователь не поймёт, что произошло. Чинить файлы нужно **до** создания поста.

## 6. Ломающее изменение: поля ошибки переехали в `extensions`

Формат объекта ошибки приведён к стандарту GraphQL. **Требует правки на клиенте.**

Заодно починились HTTP-статусы: раньше значительная часть ошибок приходила
как 500, теперь статусы корректные — 401 для авторизации, 400 для валидации,
404 для «не найдено».

**Что нужно поменять:**

```js
errors[0].code        →  errors[0].extensions.code
errors[0].statusCode  →  errors[0].extensions.statusCode
errors[0].errors      →  errors[0].extensions.errors
```

`errors[0].message` остался на месте.

Новая форма — стандартная для GraphQL. Apollo Client, urql и прочие библиотеки
читают `extensions` из коробки, отдельного кода это больше не требует.

Значения `extensions.code`: `BAD_USER_INPUT`, `UNAUTHENTICATED`, `FORBIDDEN`,
`NOT_FOUND`, `CONFLICT`, `GRAPHQL_VALIDATION_FAILED`, `SERVICE_UNAVAILABLE`,
`GATEWAY_TIMEOUT`, `INTERNAL_SERVER_ERROR`.

## 7. Требования к полям

Что проверяет сервер на входе. Стоит свериться со своим кодом —
при нарушении придёт `extensions.code: 'BAD_USER_INPUT'`.

### `initiateUploadBatch`

| Поле | Правило |
|---|---|
| `clientUploadId` | валидный **UUID** — например, `crypto.randomUUID()` |
| `originalName` | до 255 символов; запрещены `\ / : * ? " < > \|`, табы и переводы строки |
| `mimeType` | `PNG` или `JPEG` |
| `size` | от 1 до 20 971 520 (20 МБ) |
| `input` | от 1 до 10 элементов |

### `completeUpload` и `retryUpload`

| Поле | Правило |
|---|---|
| `fileId` | валидный **UUID** |
| `input` | от 1 до 10 элементов |

Лишние поля, не описанные в схеме, приводят к отклонению запроса.

Клиентскую проверку на 20 МБ **не убирайте**: пользователю лучше узнать
о превышении сразу после выбора файла, а не после запроса к серверу.

Разбор ошибки по полям приходит в `extensions.errors`:

```js
[{ field: 'clientUploadId', message: '...' }]
```

## 8. Бонус: лента больше не ломается

Отдельное исправление, действий не требует.

Раньше одна «битая» ссылка на файл в ленте роняла загрузку **всех** файлов
в этом же батче (до ~40 за запрос), и GraphQL обнулял значительную часть ответа.
Теперь ошибка затрагивает только сам проблемный файл — остальная лента приходит
целиком.

## Сводка изменений

| Что | Статус | Нужны правки? |
|---|---|---|
| `retryUpload` | новая мутация | по желанию — без неё нельзя чинить упавшие файлы |
| `completeUpload` → `failedReason`, `retryable` | новые поля, аддитивно | по желанию |
| Поля ошибки переехали в `extensions` | **ломающее** | **да** |
| `initiateUploadBatch` | сигнатура без изменений | нет |
| `createPost` | без изменений, по-прежнему требует все файлы `READY` | нет |
